## Дополнительный чек-лист

Функциональность (Features)
 Хранение файлов (вложения): Отправка файлов реализована, но не оптимальна. Сейчас клиент кодирует файл в base64 и отправляет вместе с сообщением github.com github.com, сервер сохраняет base64-данные в файл на диск (в каталог uploads/) синхронно github.com. Файл раздается как статика по пути /uploads/* github.com, а в сообщении сохраняется путь к файлу github.com github.com. Проблемы: такой подход увеличивает нагрузку на память/CPU (большие base64-строки) и диск; файлы не удаляются с диска (TTL очищает только ссылки в памяти github.com github.com, но не сами файлы). Как должно быть: загрузка файлов через multipart/form-data с потоковой передачей на сервер, сохранение на облачное хранилище или в файловую систему асинхронно, генерация ссылок для загрузки. Необходимо реализовать отдельный эндпойнт (например, POST /api/upload) для загрузки файла, который возвращает URL или ID файла. В сообщениях вместо сырых данных должны передаваться ссылки или идентификаторы. Что реализовать: на сервере с использованием middleware (например, Multer для Node/Express) обрабатывать загрузку файлов, сохранить их и возвращать метаданные. На клиенте в sendMessage вместо включения base64 вызывать API загрузки и затем отправлять сообщение с полученным file URL. Файлы для изменения: client/src/pages/messages-section.tsx (логика отправки сообщений github.com), server/src/routes/api.ts (добавить маршрут для upload и изменить обработку POST /messages чтобы ожидать ссылку вместо данных файла).
 Аудио/видео звонки: Функция частично реализована на уровне интерфейса и сигналинга, но не обеспечивает реального соединения github.com. При звонке клиент отправляет call-request через WS, отображаются модальные окна звонка (исходящего и входящего) github.com github.com. После приема вызова обе стороны открывают CallModal и начинают обмен WebRTC-сигналами через сервер (тип p2p-signal) github.com. Однако видеопоток не передается – в коде захватывается только аудио (getUserMedia({ audio: true }) без видео) github.com, а видео UI – это заглушка с иконкой github.com. Кроме того, по умолчанию ICE-сервера пусты, без STUN/TURN соединение между разными сетями почти всегда проваливается github.com. Как должно работать: при аудио- или видеозвонке клиент должен захватывать соответствующий медиапоток (микрофон и/или камеру), устанавливать одноранговое соединение WebRTC через ICE-серверы (STUN для проброса, TURN для ретрансляции при недоступности P2P). Необходимо поддерживать передачу видеопотока (добавить в SimplePeer опцию video: true и отобразить видео удаленного пользователя вместо заглушки). Сервер должен уметь оповещать клиента, если peer недоступен (например, таймаут или отклонение). Что реализовать: интеграцию TURN-сервера (например, настроить coturn и передавать VITE_TURN_URL, VITE_TURN_USER, VITE_TURN_PASS в useCallConnection/usePeerConnection для добавления ICE-серверов github.com). Добавить обработку случаев, когда собеседник не ответил: например, по таймауту автоматически посылать call-reject. Необходимые доработки в коде: в клиентском хуке звонка (client/src/hooks/useCallConnection.ts) – добавить запрашивание видео (getUserMedia({ video:…, audio:… })), передавать localStream обоих типов в SimplePeer, отобразить через <video> тэги в UI (добавить компонент для видеоэлементов вместо статичных UserIcon github.com). В server/src/ws.ts можно улучшить обработку сигналов: сейчас сигнал отбрасывается, если получатель не находится в активном чате github.com – нужно сохранять входящие p2p-signal даже если UI чата не открыт, и применить их при открытии звонка (например, хранить в очереди). Также обработать события peer.on('close'/'error'): сейчас состояние звонка не сбрасывается полностью github.com – нужно менять статус на ‘closed’ и позволять повторно звонить без перезагрузки страницы.
 Уведомления о сообщениях и действиях: В текущей версии реализованы только email-уведомления о новых сообщениях, когда получатель офлайн github.com. Внутри приложения – всплывающие уведомления (toasts) о новом сообщении показываются, если сообщение пришло от пользователя, с которым сейчас нет открытого чата github.com. Недостающие функции: нет push-уведомлений на мобильных устройствах, нет системных уведомлений ОС (для Electron клиента) при получении сообщений или звонков. Также нет уведомлений о пропущенных звонках. Как должно работать: пользователю должны приходить уведомления о новых сообщениях/звонках даже если приложение свернуто или пользователь не смотрит текущий чат. В веб/Electron можно использовать Notification API для системных уведомлений, в мобильных платформах – интегрировать push-уведомления (через Firebase Cloud Messaging или аналог). При пропущенном звонке должна появляться заметка о пропущенном вызове (например, в списке чатов). Что реализовать: добавить на сервере сохранение событий пропущенного звонка (если отправлен call-request, но не был принят в течение таймаута – сохранить как “missed call” в БД или отправить специальный чат-сообщение типа “Missed call”). Клиент при следующем открытии приложения или при синхронизации мог бы отобразить эти события. Для push-уведомлений – реализовать в сервере отправку через FCM: например, сохранять FCM-токены для пользователя при входе, и при офлайн-сообщении или звонке использовать HTTP API Firebase для пуша. Задействованные модули: server/src/util/email.ts уже есть для email; можно добавить server/src/util/notifications.ts для push (с использованием внешней библиотеки FCM). На клиенте – в сервис-воркере (для веб) или в Electron main процессе – вызывать Notification API при получении события через WS (например, на событие chat или call-request отображать системный notification).
 Групповые чаты: Поддержка групп и каналов объявлений частично начата, но не завершена. В коде присутствуют компоненты UI для “Groups” и “Announcements” github.com, схемы данных для Group с полем members github.com, и возможность создать группу/анонс из интерфейса github.com github.com. Однако на сервере отсутствуют маршруты /api/groups – в API-роутере они не подключены (не импортирован никакой groupsRouter). Фронтенд пытается читать /api/groups и /api/groups/{id}/users github.com, что вернет 404. Как должно работать: пользователи должны иметь возможность создавать групповые чаты, добавлять участников, отправлять туда сообщения. Каналы объявлений – по сути те же группы с флагом isAnnouncement (только админ или создатель может писать, остальные только читают). Что нужно реализовать: на сервере – модель групп (таблицы groups, group_members, и, возможно, использовать существующую таблицу messages с полем group_id). Реализовать эндпойнты: создание группы (POST /api/groups), получение списка групп пользователя (GET /api/groups – например, группы, где пользователь состоит), добавление/удаление участника (POST/DELETE /api/groups/:id/members). Для объявлений – либо отдельная таблица, либо использовать ту же с флагом; при создании с isAnnouncement:true добавить всех пользователей по умолчанию или помечать особым образом. Файлы: требуется написать новый модуль маршрутов server/src/routes/groups.ts и подключить в api.ts. В клиенте – доработать GroupsSection для отображения списка групп (вместо заглушек) и открытия чата группы (возможно, переиспользовать существующий MessagesSection, адаптировав на наличие groupId). Также необходимо в механизме WebSocket добавить тип сообщений group-chat и рассылку их всем участникам группы.
 Wiki (база знаний): Имеются зачатки раздела “Wiki” – схема WikiEntry и API-клиент на фронте github.com, но функциональность не доведена. В интерфейсе при переходе в Wiki отображается заглушка “feature temporarily unavailable” github.com. Как планировалось: корпоративная база знаний с категориями и статьями, доступными для чтения/редактирования. Судя по коду, должны быть категории (/api/wiki/categories) и записи /api/wiki/entries с CRUD операциями github.com github.com. Что нужно для реализации: создать на сервере маршруты wiki.ts (возможно, они есть, но не подключены) для получения списка статей, категорий, создания и изменения статей. Скорее всего, нужна таблица wiki_entries (поля: id, category_id, title, content, author, т.п.). Реализовать Markdown-редактор или простой редактор текста на клиенте для создания/редактирования записей. Файлы: проверить существование server/src/routes/wiki.ts (подключить его через api.ts). Дополнить клиентские компоненты WikiSection, WikiArticlePage – вместо заглушки выводить список категорий и статей, форму создания/редактирования (можно использовать React Quill или простой <textarea>). Учесть ограничения прав: возможно, только админы или определенные роли могут создавать/редактировать статьи – это связывается с вопросом безопасности/авторизации (см. ниже).
Безопасность (Security)
 Хранение сессий и авторизация: В приложении используется сессия на express-session с in-memory store по умолчанию github.com. Это небезопасно и непрактично в продакшене – сессии потеряются при перезапуске, не масштабируются на несколько экземпляров сервера, и cookie не настроены как secure. Рекомендации: включить cookie.secure и sameSite=strict для продакшена (требует HTTPS) github.com. Для масштабирования – использовать внешнее хранилище сессий (Redis/Memcached) или перейти на stateless авторизацию (JWT). JWT токены можно хранить в localStorage/Memory на клиенте и отправлять в Authorization header – это облегчит масштабирование (не нужно общая сессия). Однако JWT стоит внедрять осторожно (обеспечить их недолгое время жизни и возможность отзыва). Альтернатива: в корпоративной среде рассмотреть интеграцию с SSO/LDAP – например, реализовать OAuth2/OpenID Connect login через корпоративный провайдер, чтобы не хранить пароли вообще.
 Пароли и учетные записи: Сейчас пароли хранятся в БД в хешированном виде (bcrypt) – это хорошо github.com. Но отсутствует валидация сложности пароля и подтверждение email. Пользователь может зарегистрироваться с любым email, и система сразу авторизует его (авто-логин после регистрации) github.com. Это может привести к проблемам в случае опечатки в email – аккаунт будет создан без верификации. Решение: добавить отправку письма подтверждения регистрации – до подтверждения не давать доступ в систему. Также ввести политику сложности пароля (минимум длина, требования к символам) – это можно проверить на клиенте и сервере (например, Zod-схемой или отдельной логикой). Ограничить попытки логина (например, капча или временная блокировка после нескольких неудач) – сейчас такого нет, можно брутфорсить пароли. Для реализации rate-limiting логинов использовать например express-rate-limit middleware.
 Роли и разграничение прав: В коде присутствует поле is_admin у пользователя github.com и некоторые админ-функции (например, выполнение произвольного SQL) ограничены проверкой is_admin на сервере github.com. Однако в интерфейсе нет разграничения: нет панели администрирования (кроме упомянутого скрытого эндпойнта). Любой вошедший пользователь может вызвать API доступные ему, но, например, нет проверки прав на действия с заявками: сейчас PATCH /api/requests/:id/accept не проверяет, что пользователь принадлежит нужному департаменту – любой авторизованный может попытаться принять любую заявку github.com. Аналогично, завершить заявку может кто угодно github.com. Необходимо: реализовать систему ролей/прав. Например, добавить поле роль (role: user, support, admin и т.д.) и на сервере проверять в middleware или вручную: принимать заявку может только пользователь, чей department совпадает с receiver_department_id заявки; завершить – либо тот, кто принял (поле who_accepted), либо админ. Эти проверки добавить в соответствующие обработчики запросов. Файлы: server/src/routes/requests.ts – добавить логики проверки после L49 и L65. Клиентскую часть – скрывать или отключать кнопки, если у пользователя нет прав (например, не показывать “Принять” тем, кто не является исполнителем). Также предусмотреть в будущем раздел “Admin” – управление пользователями, модерация Wiki и пр., доступный только admin.
 Веб-безопасность (XSS, CSRF): Приложение построено как SPA с API, что уменьшает риски CSRF (ограниченный origin CORS github.com и SameSite cookies). XSS риск снижен за счет того, что пользовательский ввод (сообщения, имена) выводится через React в текстовых узлах, что экранирует HTML. Например, сообщения вставляются как {m.content} в JSX github.com – вредоносный скрипт в тексте не исполнится. Однако потенциальная опасность есть в Wiki (если будет HTML-контент) – нужно либо экранировать на сервере, либо использовать Markdown/проверенный рендер. SQL-инъекции в запросах подавлены использованием параметров $1, $2 везде github.com. Уязвимое место: эндпойнт admin SQL позволяет выполнить любой запрос в БД github.com, хоть и требует is_admin. Если злоумышленник получит доступ к кукам админа, он может дистанционно выполнить произвольный SQL на бэкенде. Митигация: ограничить использование /api/admin/sql в продакшене (например, включать только в режиме разработки), или требовать дополнительную авторизацию (2FA для админа). Либо вовсе убрать эту функцию после отладки.
 Протоколы и шифрование: На момент анализа приложение не гарантирует шифрование медиа при звонках и шифрование данных end-to-end. Звонки идут по WebRTC – медиа трафик там шифрован DTLS-SRTP автоматически, но сигналинг по WS – нет шифрования содержимого (кроме TLS самого WS, если использовать wss://). Сообщения хранятся в открытом виде в БД (без E2EE). В корпоративном контексте это обычно приемлемо (сервер – доверенная сторона), но следует как минимум обеспечить HTTPS/WSS в продакшене (включить SSL, использовать wss:// для WebSocket). В Supabase-конфиге указан HTTP для API студии github.com – нужно поменять на HTTPS в боевой среде. Рекомендация: получить и подключить SSL-сертификат, настроить reverse proxy (Nginx) для TLS, выставить secure куки. Для максимально конфиденциальных чатов можно рассмотреть внедрение End-to-End шифрования: например, обмен публичными ключами между пользователями и шифрование сообщений на клиенте. Это потребует значительных изменений (хранить зашифрованные сообщения, реализовать протокол обмена ключами, недоступность истории при утрате ключа и т.д.), поэтому внедряется по необходимости. Первичный шаг – хотя бы шифрование на транспортном уровне (TLS) и защита базы (например, шифрование диска сервера или отдельных полей, если требуется соблюдать политики безопасности).
UI/UX
 Мобильный интерфейс и адаптивность: Имеются проблемы отображения на малых экранах. Боковое меню (Sidebar) на мобильном имело прозрачный фон, из-за чего контент просвечивал github.com. Dropdown-меню не имело фона из-за недостающей настройки Tailwind цвета popover github.com. Решение: задать явный фон боковой панели (например, класс bg-white dark:bg-gray-900 для света/темноты) и убедиться, что она перекрывает фон (например, z-index выше задника). Для выпадающего меню – добавить в tailwind.config.cjs цвет popover и использовать его класс в стилях Dropdown, чтобы бэкграунд появлялся. Проверить генерацию этих классов в продакшен-сборке (возможно, запустить npx tailwindcss для обновления). Также убедиться, что все основные компоненты адаптируются: например, список контактов скрывается на мобильном при открытом чате (уже есть логика скрывать при выбранном чате на малых экранах github.com).
 Обратная связь и ошибки: В текущей версии пользовательский опыт страдает от отсутствия явных уведомлений об ошибках. Пример: на странице регистрации клиент не отображает текст ошибки от сервера – в коде неправильно читается поле (errorData.message вместо errorData.error) github.com, из-за чего при ошибке (например, занятый username) пользователь получает пустой ответ. Также при разрыве соединения после нескольких попыток переподключения пользователь не информирован, что связь потеряна github.com. Исправление: вывести сообщения об ошибках из ответа сервера (например, если приходит { error: "Invalid credentials" }, показать этот текст). На странице входа/регистрации нужно добавить отображение ошибок под формой. При разрыве WS после исчерпания попыток – показывать баннер “Соединение с сервером потеряно” и кнопку “Переподключиться” github.com. Также предусмотреть автоматическое разлогинивание при коде закрытия WS 4401 (неавторизован) – сейчас клиент бесконечно пытается переподключиться, оставаясь на экране загрузки github.com. Нужно в обработчике onclose WS проверить код и выполнить logout() с уведомлением пользователю.
 Когерентность UI и сценарии: Есть некоторые несоответствия в пользовательском потоке. Например, после регистрации сервер сразу авторизует сессию github.com, но клиент этого не ожидает – форма регистрации просто возвращает 201, и пользователь остается на странице логина, хотя уже зарегистрирован и залогинен на сервере. Это сбивает с толку. Решение: решить, какой сценарий желателен. Проще – автовход: тогда клиент после успешной регистрации должен сразу получить текущего пользователя (GET /api/user) и перенаправить в приложение (в чат). Либо отключить авто-логин на сервере (не выставлять isonline, не сохранять в сессию) и попросить пользователя войти вручную – менее удобно. Предпочтителен автологин, поэтому доделать клиент: после ответа 201 на регистрацию вызвать тот же код, что при логине (обновить контекст auth, перейти на HomePage). Кроме того, навигация между разделами: пока разделы “Groups”, “Wiki” и др. существуют, но не все работают – при клике на них пользователь видит placeholder или пустую страницу. Стоит либо убрать неготовые разделы из меню, либо отметить их как “(в разработке)” для ясности.
 Эстетика и удобство: Некоторые мелочи UI можно улучшить. Например, при прикреплении нескольких файлов сейчас превью просто выводятся списком, но нет индикатора прогресса отправки каждого файла. Стоило бы отображать статус загрузки/отправки (пока message.status = 'pending'). Иконки файлов: реализовано отображение эмодзи/метки по расширению файла (PDF, ZIP и пр.) github.com github.com – это хорошо, но можно добавить эскизы для изображений и PDF (генерировать превью). Локализация: В коде есть использование react-i18next и множество ключей (t('...')) для переводов, однако нужно убедиться, что все строки переведены на нужные языки. Возможно, не все тексты вынесены (например, placeholder “Content goes here...” в RequestModal заглушке не локализован github.com). Следует провести ревизию i18n. Консистентность дизайна: убедиться, что во всех компонентах используются единые UI-компоненты из библиотеки (кнопки, инпуты) для одинакового стиля. В частях интерфейса, связанных с незавершенными функциями, сейчас могут быть резкие переходы (напр., пустая страница Wiki). Лучше показывать пользовательское сообщение типа “Раздел находится в разработке” (как сделано для Wiki).
 Пропущенные вызовы и индикация звонков: Сейчас, если звонок поступает, всплывает диалог с кнопками принять/отклонить github.com, но нет звукового сигнала вызова. Стоит добавить звук звонка (воспроизводить аудио файл рингтона при входящем call-request и останавливать при ответе/отклонении). Если вызов пропущен – как упомянуто, пользователь этого не узнает при следующем входе. В журнале чата можно отображать системное сообщение “Вызов пропущен” или иконку в списке контактов. UX-деталь: После завершения звонка хорошо бы показать длительность вызова или статус (сейчас таймер звонка идет, но по закрытии окна информация теряется). Можно в историю сообщений добавлять запись о звонке (например, “Вы звонили X, длительность 00:02:35”).
Масштабируемость и производительность
 Хранение сессий и масштабирование серверов: Как отмечалось, использование MemoryStore для сессий не позволит запустить несколько экземпляров сервера – пользователь может потерять сессию при балансировке. Для масштабирования по горизонтали нужно вынести сессии в общее хранилище (Redis). Альтернативно – перейти на JWT и sticky sessions не потребуется. Также WebSocket-соединения сейчас хранятся в памяти одного процесса (connections Map в ws.ts github.com). В кластерном окружении сообщения между пользователями на разных нодах не дойдут. Решение – либо применять sticky sessions на уровне балансировщика (все запросы от пользователя X всегда на одну ноду), либо использовать внешний брокер сообщений (например, Redis Pub/Sub) для рассылки WS-сообщений между узлами. В Node можно внедрить ws с использованием Redis store (например, ws + redis-adapter аналогично Socket.io). В настоящем корпоративном приложении это обязательный шаг для масштабирования чата.
 Отсутствие пагинации и оптимизации запросов: Клиент запрашивает все сообщения диалога сразу (в коде refetchHistory() тянет всю историю) – это будет тормозить при большом количестве сообщений. Нужно реализовать ленивую подгрузку (напр. при прокрутке вверх подгружать старые сообщения). Также /api/contacts возвращает всех пользователей разом. В небольшой компании это ок, но в большой – лучше реализовать поиск сервером и подгружать порциями (например, по алфавиту или “постранично”). Оптимизация: убедиться, что в БД есть индексы на поля фильтрации (скорее всего, на messages.sender_id/receiver_id, users.department_id). Если планируется много сообщений, рассмотреть шардинг или архивирование старых сообщений.
 Работа с файлами и памятью: Отправка файлов base64 увеличивает нагрузку: 1) ~33% рост размера (base64), 2) высокое потребление памяти при чтении/записи (Buffer.from(base64, 'base64') держит весь файл в памяти). При многих одновременных отправках сервер может испытывать нехватку памяти или GC-паузы. Решение: как указано, перейти на стриминг файлов. Также, сейчас fs.writeFileSync блокирует поток Node на время записи файла github.com – это может задерживать обработку других запросов. Нужно перейти на асинхронный метод (fs.promises.writeFile или поток). В идеале – вынести хранение файлов в отдельный сервис (например, AWS S3, MinIO или Supabase Storage) чтобы сам сервер не занимался IO файлами. Это разгрузит сервер и упростит масштабирование (файлы доступны независимо от конкретного инстанса сервера).
 Использование сторонних сервисов (Supabase): В репозитории присутствует конфигурация Supabase github.com, что намекает на попытку использовать Supabase (Postgres, realtime, auth) для хоста. Однако фактически сервер – самописный Express. Возможно, Supabase разворачивался для быстрого старта БД. Если планируется использование Supabase Realtime (подписки на изменения), то часть функционала (например, уведомления о новых сообщениях) можно было бы реализовать через Supabase. Пока это не используется. В контексте масштабируемости, Supabase мог бы обеспечить масштабируемый бэкенд (БД + вебсокеты), но интеграция не завершена. Решать, оставаться ли на своем сервере или перейти к использованию Supabase полностью (требует перевода логики на SQL/хранимки и клиентские подписки). Если остаемся на Express, Supabase-конфиг можно убрать, либо использовать только как БД.
 Логи и мониторинг: В приложении используется pino и morgan для логирования запросов github.com, но нет централизованного сбора логов и метрик. В продакшене для масштабирования важно иметь мониторинг: количество активных пользователей, потребление памяти (особенно из-за in-memory store) и пр. Рекомендация: внедрить инструмент типа PM2 или Docker-контейнеры, настроить сбор логов в Elastic/Kibana или другой лог-агрегатор. Также реализовать обработку непойманных ошибок (unhandledRejection, uncaughtException) чтобы сервер не падал без записи ошибок. Для клиента – можно интегрировать сервис сбора ошибок (например, Sentry) чтобы отслеживать проблемы UI у пользователей. Это не прямая масштабируемость, но важно для стабильности при росте пользователей.
